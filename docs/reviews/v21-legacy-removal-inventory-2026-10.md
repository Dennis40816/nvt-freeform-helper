# V21/Legacy Complete Removal Inventory (2026-10)

## Purpose, Scope, and Evidence Boundaries

This document supports the owner's later decision on the scope and version for "complete removal of V21/Legacy". The owner has confirmed that 「2.1」 means Notch V21; the owner decided (2026-10-04, relayed by Commander) that complete removal comes after 1.3.x, with the scope to be decided later and no implicit conversion before then. The target version is not set; this document proposes no version, date, or authorization to execute. Under the 2026-10-03 decision in `TODO.md` and `docs/guides/refactor-roadmap-1.3.x.md`, the current stage retains the original V21/Legacy behavior and zero-diff gates, with no further investment in additional legacy convergence/equivalence work.

The inventory is based on branch `feature/queue/v21-legacy-removal-inventory`, commit `7477b07d3969ad6ad15960d0d1ac8b60ef37a9bc`. `AGENTS.md`, the dependency graph, and domain/reference documents were read first; the `ProjectReference` entries of the existing five projects match the dependency graph, so no rebuild is needed. There is no `.codegraph/`; searches were limited to `src/`, `tests/`, `scripts/`, `docs/`, and root-level documents.

No content under `example/` was read, listed, or verified. The private data paths below come only from test/script source code and public documents; the commander still needs to check in an allowed environment whether the data remains complete, the modes of actual projects, the golden content, and coverage counts. No private payload was brought into this document.

Three scopes must be decided separately:

| Scope | Current state | Removal impact |
| --- | --- | --- |
| V21 output version | `NotchAlgorithmVersion.V21`; CadAllocation can also produce V21, so it is not used only by Legacy mode | V21 rows, Q7 firmware ABI, C v2.1, V21 in CSV, simulation, and UI/IPC options |
| Legacy computation mode | `NotchComputationMode.LegacyRegularAnchor`; can produce V21 **and V22** | regular-anchor geometry, nine-column compatibility rows, request-specific table cache, reproduction of old projects |
| Other support named legacy/Q7 | V22 raw-values reader, shared allocation Q7, Step3 legacy inline rule gate, old UI snapshots, etc. | Not equivalent to the first two scopes; assess by consumer, not by deleting every matching string |

## Risks and Questions Still Requiring Owner Answers or External Evidence

- **Existing firmware may accept only the V21 ABI.** V21 UINT8 Q7 ADD/SUB and destination rows differ from V22 INT8 signed percent/source rows and function contracts; changing the option to Cv22 cannot be treated as a compatible replacement. Evidence of requirements for downstream firmware models/users/delivered projects is still needed.
- **Legacy is not an alias for V21.** Legacy V22 matched-regular geometry and neighbor lengths differ from normal CadAllocation canonical allocation; changing mode can change row counts, directions, payload, and simulation. The current zero-diff results for each version do not imply that the two modes are equivalent.
- **Old files may be silently rewritten.** Enabled-set fallback, linked threshold, app/project Cv21 preferences, and unknown nested fields not preserved by ExtensionData can all change subsequent exports during Load→Save. Migration must explicitly disclose behavioral changes; rejection must take effect before execution/saving.
- **Names alone cannot determine deletion.** V22 still uses `NotchV21FirmwareEvaluator.QuantizeToFirmwareInt16`; `NotchThresholdQ7Contract` still serves `NotchAllocationService` and `NotchV22CompensationService.Stages`; the `ThresholdQ7`/`MaxAllocationQ7` comparison in Notch Detail is also a shared UI consumer. The legacy inline gate for `EnableToFullRuleEngine=false` differs from the LegacyRegularAnchor in this scope.
- **The raw V22 reader boundary needs a separate decision.** The raw-values constructor in `NotchTableRow.cs:NotchTableRow`, raw V22 fallbacks in `NotchV22FirmwareProjector.cs:ProjectRow` and `NotchValidationTraceService.cs:BuildV22Payload`, and the values fallback in `NotchCadOutputFwDiffProjectionService.cs:ProjectRow` must not be deleted just because they involve legacy/nine columns; validation currently includes only V22 rows. Whether this goal includes such public raw-input contracts has not been specified.
- **UI/IPC/CSV and baselines may all have external consumers.** Retiring `enableV21`, `Cv21`, version_code=21, nine-column CSV, and Legacy count/timing changes visible text or schemas; whole-class counts are not counts of cases that can be deleted. After removal, retain regression protection for V22 state/cache/invalidation, sentinel, INT16/EMS, etc.
- **Private golden data has not been verified.** This round did not inspect modes in the data, nonzero linked thresholds, or the distribution of delivered projects; the public 3635 baseline declares CadAllocation/both versions with threshold=0 and cannot represent all Legacy projects. Nor has confirmation been obtained that downstream firmware can retire V21.
- **Governance and acceptance policies have not changed.** The owner's current retention requirement and existing 1.3.x two-version zero-diff/append-only constraints remain; a new decision is needed on which gates/old-file policies can exit at complete removal. This document does not select a version or approve breaking behavior for the owner.
